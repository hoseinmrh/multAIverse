# Build “Multiverse” — A Personal Alternate-Life Simulator

You are the lead software engineer, product designer, game-systems designer, and technical architect for this project.

Build a polished, local-first application named **Multiverse**. It allows a user to explore fictional alternative versions of their life resulting from major decisions.

This must be a functional application, not merely a UI mock-up or architectural proposal.

Work autonomously. Make sensible technical and product decisions when details are unspecified. Do not stop after writing a plan. Create the plan, then implement the application.

After every major implementation phase:

1. Run relevant tests.
2. Run linting and type checking.
3. Fix failures before continuing.
4. Update the project documentation.
5. Summarize completed work in `docs/PROGRESS.md`.

Do not claim that something works unless you have run the relevant command or test.

---

# 1. Product vision

Multiverse is a fictional strategy and storytelling game in which users simulate alternate versions of their lives.

The user creates a profile representing their current situation and enters a major decision, such as:

* Stay in industry.
* Pursue a PhD.
* Launch a startup.
* Move to another country.
* Change career.
* Continue an abandoned project.
* Prioritize relationships, money, health, research, or freedom.

The application creates several branching universes. Each universe develops through choices, random events, delayed consequences, changing statistics, relationships, achievements, failures, and generated artifacts.

The application should feel like a combination of:

* A narrative life simulator.
* A strategy game.
* An interactive timeline.
* A visual multiverse map.
* A conversation with possible future selves.

This is an entertainment and reflection tool. It must never present its results as reliable predictions, financial advice, medical advice, or career guarantees.

Display a visible disclaimer:

> Multiverse creates fictional scenarios for entertainment and reflection. Its simulations are not predictions or professional advice.

# 2. Initial MVP goal

The first complete version must support this end-to-end flow:

1. The user creates or selects a personal profile.
2. The user enters one major life decision.
3. The application generates three alternative universes.
4. Each universe receives:

   * A name.
   * A visual identity.
   * An initial direction.
   * A starting location and career.
   * Initial statistics.
   * A short premise.
5. The user opens the multiverse map.
6. The user selects a universe.
7. The user advances time by one year.
8. The simulator generates events and important decisions.
9. The user chooses between event options.
10. The deterministic engine applies immediate and delayed effects.
11. The timeline and statistics update.
12. The user can simulate at least five years.
13. The user compares the three universes.
14. The user opens a conversation with one future self.
15. The user views fictional artifacts generated by each universe.

The complete core experience must work without an OpenAI API key by using a high-quality mock narrative provider.

An optional OpenAI provider should enhance narrative generation when an API key is configured.

# 7. Deterministic simulation engine

The language model must not directly control statistics or database state.

Implement a deterministic engine that owns:

* Time advancement.
* Statistic changes.
* Financial calculations.
* Career progression.
* Requirements.
* Choice validity.
* Delayed effects.
* Random-event selection.
* State snapshots.
* Score normalization.
* Reproducibility.

The narrative provider may propose events and choices, but the deterministic engine validates and applies them.

## Reproducibility

Every scenario and universe must have a random seed.

Given the same:

* Starting profile.
* Scenario.
* Universe seed.
* Previous choices.
* Simulation mode.

The deterministic portion of the simulation should produce the same result.

Use a seeded pseudorandom number generator. Do not use uncontrolled global randomness.

## Statistic rules

Provide reusable functions for:

* Clamping values between 0 and 100.
* Applying positive and negative modifiers.
* Applying diminishing returns near 100.
* Applying stronger penalties when stress remains high.
* Applying health penalties after prolonged extreme stress.
* Calculating happiness from several factors without making it a simple average.
* Calculating career progression from skill, opportunity, discipline, and choices.
* Calculating research impact from focus, network, output, and randomness.
* Calculating startup outcomes from execution, timing, network, funding, and risk.
* Calculating annual income and net-worth changes.

Avoid implying that high income automatically creates high happiness.

## Annual simulation order

When advancing one year:

1. Load the latest state.
2. Apply due delayed effects.
3. Apply baseline yearly changes.
4. Evaluate active flags.
5. Select routine events.
6. Generate or select one significant event.
7. Create choices when user input is required.
8. If no choice is required, resolve the event automatically.
9. Apply validated effects.
10. Generate zero to two artifacts.
11. Produce a yearly summary.
12. Save a new immutable state snapshot.

Do not advance beyond an unresolved important choice.

## Effects format

Use a validated structure such as:

```json
{
  "stats": {
    "career_level": 4,
    "research_impact": 8,
    "stress": 6,
    "happiness": -2
  },
  "finance": {
    "monthly_income_delta_eur": 300,
    "net_worth_delta_eur": -2000
  },
  "set_flags": ["living_abroad"],
  "remove_flags": [],
  "skill_changes": {
    "robotics": 5,
    "leadership": 2
  }
}
```

Reject unknown statistics and malformed effects.

## Delayed effects

A choice can create later consequences.

Example:

```json
{
  "trigger_after_years": 2,
  "probability": 0.35,
  "description": "The research collaboration leads to a startup opportunity.",
  "effects": {
    "stats": {
      "career_level": 5,
      "reputation": 4,
      "stress": 3
    },
    "set_flags": ["startup_opportunity"]
  }
}
```

When a probability is evaluated, use the universe’s seeded random generator.

# 8. Simulation modes

Support these modes:

## Realistic

Plausible careers, financial progress, setbacks, and opportunities. Events should remain grounded.

## Cinematic

More dramatic opportunities, reversals, rivalries, public recognition, and major turning points.

## Utopian

Explores highly positive but still internally coherent outcomes.

## Dark

Increases setbacks, burnout risk, financial pressure, failed opportunities, and difficult trade-offs.

## Chaos

Permits absurd but narratively consistent events.

Examples:

* A robotics prototype becomes an international internet celebrity.
* An academic paper is accidentally interpreted as a philosophy manifesto.
* The user becomes mayor of Trento after a sequence of improbable events.
* A coffee machine developed during a hackathon gains venture funding.

Mode changes should influence event selection and tone, but should not bypass the deterministic engine.

```python

    async def generate_significant_event(...): ...
```

## MockNarrativeProvider

Requirements:

* Works without internet access.
* Produces coherent demo content.
* Uses profile details, universe direction, current state, previous events, and simulation mode.
* Includes enough templates and variation that the demo does not feel completely static.
* Uses the universe seed for reproducible selection.
* Produces data conforming to the same Pydantic schemas as the OpenAI provider.

## OpenAINarrativeProvider

This provider is optional at runtime but must be implemented.

Requirements:

* Enabled only when `NARRATIVE_PROVIDER=openai`.
* Reads the API key from `OPENAI_API_KEY`.
* Reads the model name from `OPENAI_MODEL`.
* Makes requests only from the backend.
* Never sends the API key to the browser.
* Uses the OpenAI Responses API.
* Uses Structured Outputs or strict JSON-schema validation.
* Validates every response with Pydantic.
* Retries only a small, bounded number of times.
* Uses sensible timeouts.
* Handles invalid output gracefully.
* Falls back to the mock provider when configured to do so.
* Logs errors without logging API keys or sensitive profile content.
* Does not hardcode a model that may become unavailable.
* Documents configuration in `.env.example`.

# 24. MVP acceptance criteria

The MVP is complete only when all of the following are true:

* A new developer can set up the project using the README.
* The frontend and backend start locally.
* The database can be created and seeded.
* The demo works without an API key.
* The demo contains three distinct universes.
* The multiverse graph displays all three branches.
* A universe can advance through five years.
* Significant events produce choices.
* Choices modify state exactly once.
* Delayed effects are applied in later years.
* Statistics remain within valid ranges.
* Timeline snapshots are preserved.
* At least three artifact types are displayed.
* The three universes can be compared.
* Future-self chat works in mock mode.
* OpenAI mode is available through environment configuration.
* AI-generated payloads are schema-validated.
* OpenAI failure does not corrupt simulation progress.
* Backend tests pass.
* Frontend checks pass.
* The Playwright happy-path test passes.
* Linting and type checking pass.
* The README and architecture documentation are complete.
